# 开发需求评估与"切片"方案

- 版本：v1.0
- 关联文档：`docs/01-需求整合与项目架构.md`
- 结论先行：**需要切片，建议切成 5 个开发切片 + 1 个契约/收口阶段（Lead）**。切片以"文件写作用域互不重叠 + 只依赖冻结契约"为边界，可在同一工作区并行推进。

---

## 一、评估方法

1. 先落需求与架构（已完成），把系统拆成 6 个可独立验收的能力域；
2. 对每个能力域估算代码量、耦合度、不确定性（见 2.1）；
3. 用"能否在契约冻结后独立开工、且改动的文件不重叠"作为可切片判据；
4. 不可切的部分（契约、骨架、集成、真机验证）留给 Lead 串行完成。

代码量按实现复杂度估算（含注释与必要容错），不含测试脚本。

### 1.1 能力域评估

| 域 | 内容 | 预估代码量 | 耦合 | 不确定性 | 可独立开工 |
|---|---|---|---|---|---|
| **A 采集层** | 魔数嗅探；OOXML 读取（zip+XML 流式）；BIFF8/OLE2 读取；CSV（含 GBK/UTF-8 嗅探） | 900–1100 行 | 只依赖 `WorkbookModel` | **高**：老格式边界多（已用探针验证主路径可行，见下） | 是 |
| **B 结构识别与归一化** | 多级表头识别、合并传播、数据区/小计/占位行判定、单元格归一化（全半角/空白/日期/数值/手机号） | 500–700 行 | 依赖 A 的单元格模型 | 中高：判据要靠真实样本调 | 是（用样本 + 手写 fixture） |
| **C 索引与检索** | 2-gram 倒排、增量刷新、查询解析（AND/OR/短语）、打分、片段高亮、结果导出 | 500–700 行 | 依赖 B 的 `TableModel` | 中：算法确定 | 是（契约 + mock 表） |
| **D 字段映射与模板改造** | 模板登记/替换（解析表头 + 用户框选数据起始格）、别名词典+相似度自动推荐、**坐标化映射规则引擎（列→列 / 行→列转置 / 区域块）**、方案 CRUD、**模板 zip 克隆注入**（保样式）、数值/日期按 numFmt 写入、逐单元格预演 | 1200–1600 行 | 依赖 B | **高**：xlsx 包结构 + 保样式 + 转置语义 | 是（模板样本已具备） |

| **H 编辑写回** | 冲突检测、备份、zip 条目级最小改动写回（文本/数值/公式/合并拒绝）、写后重解析自检、自动回滚、审计日志、撤销、增量索引更新 | 700–900 行 | 依赖 A 的读取、S0 契约 | **高**：写坏文件不可逆 | 是（xlsx 样本现成） |
| **F Web 前端** | 5 个页面、网格预览、**映射矩阵 + 区域框选 + 预演**、单元格编辑弹窗、查找替换、差异三色着色、轮询任务、下载 | 1500–1900 行 | 只依赖 API 契约 | 中 | 是（用 mock JSON） |
| **G 服务骨架/契约/集成** | `model.py` 契约、`server.py` 路由、静态托管、任务与下载令牌、端到端联调、打包脚本、README | 500–700 行 | 全局 | 低 | 否（必须 Lead 串行） |
| 测试 | 单测（各解析器/识别/索引/映射/对比/写回）+ 端到端（真实样本） | 900–1100 行 | 跟随各域 | 低 | 可分摊 |

**合计 ≈ 7300–9500 行**（不含前端静态资源），属于"单人串行 4–6 天、并行 1 天内可收口"的体量。

### 1.2 已消除的最大不确定性（探针结论）

`scripts/probe_xls.py` 用**纯标准库**（`struct`）实现了 CFB + BIFF8 读取，已在 3 个真实 `.xls` 上跑通：

- `示例预警.xls`：2 个表，600 单元格，115 条共享字符串，数字/文本/日期混排 ✓
- `11月2日…工单4件(1).xls`：45 单元格 ✓
- `示例表格C.xls`：161 单元格，7 列 ✓

同时实测确认：`.et` 有两种容器（一个 zip、一个 OLE2），所以**必须按魔数而非扩展名分流**；目标机无网络、无 xlrd、无 LibreOffice，因此"零依赖自研解析"是唯一可行路线。→ **切片 A 的主要风险已从"能不能做"降为"边界覆盖多少"。**

## 二、切片结论

**需要切片。** 判据：

1. 体量：6k+ 行、6 个能力域，单 Agent 串行执行上下文与时间成本都高；
2. 耦合：A→B→{C,D,E} 是单向依赖，配合冻结契约即可并行；F 只依赖 API 契约，可与后端同时开工；
3. 冲突面：每个切片改动的目录完全不同（见 4.3 写作用域），天然适合同工作区并行；
4. 但 G（契约/骨架/集成）与 A+B 强耦合于真实样本，**不能切**，需要 Lead 先冻结契约并亲自收口。

**为什么不是 3 片**：3 片会让 D（最重、最不确定）独占一片且无人并行分担，P1 阶段其他片空转。
**为什么不是 8 片**：再拆就要把 A 的 OOXML/BIFF 分给两人，但两者共用 `model.py` 且都要在同一批样本上联调，沟通成本高于收益；F 再拆会共享同一份 `app.js`，产生写冲突。

### 2.2 并行执行计划

```
阶段 P0（串行，~30–40 min）
  Lead：冻结 model.py / JSON API / 目录骨架 / mock 数据 / 启动.bat
        └─ 门禁：契约 import 通过、空壳服务能起、mock 可被前端读取
                │
阶段 P1（并行，~90–120 min）────────────────────────────────────
  S1 采集层      S2 结构识别        S6 前端(对 mock)      S4 模板登记+克隆探路
  （S2 用 S1 的模型契约 + 自造 fixture 先行；S4 先把模板包结构与"数据行克隆"跑通）
                │                    │
阶段 P2（并行，~90 min）────────────────────────────────────────
  S2 收尾 → S3 检索   S4 映射引擎+区域转置   S5 双表对比+坐标
  S8 编辑写回         S6 对接真实 API
                │
阶段 P3（Lead 收口，~60–90 min）
  联调 → 真实目录回归 → 验收清单 → README/打包
```

**关键同步点（必须对齐，否则返工）**：

1. **P0 结束**：`model.py`（含 `CellRef`/`TemplateDef`/`MappingRule`/`EditOp`）、API 请求/响应 JSON 结构、错误码 —— 冻结后任何变更必须 Lead 广播；
2. **P1 中段**：S1 交付 `WorkbookModel` 真实实现，S2 用它替换 fixture；
3. **P2 开始**：S2 交付 `TableModel` 真实实现，S3/S4/S5/S8 从 mock 切真实数据；
4. **P2 结束**：S3/S4/S5/S6/S8 各自 API 可调通，Lead 开始端到端。

### 2.3 写作用域与冲突规避

- 每个切片只写自己表内的目录；`app/core/model.py`、`app/core/cellref.py`、`app/server.py`、`app/api.py` **只有 Lead 能改**；
- 若某切片确实需要改契约：先在群内提出，由 Lead 改并广播新版本号（`CONTRACT_VERSION`），不允许各自偷偷加字段；
- `app/web/index.html` 由 S0 定骨架，S6 只能改 `app/web/pages/*`、`app/web/app.js`、`style.css`；
- **写回（S8）只动自己的 `writers/`、`audit.py`、`edit_service.py`**，不得触碰 `readers/`；S4 只动 `template.py`/`mapping.py`/`xlsx_writer.py`，两者互不越界；
- 测试文件按域分目录：`tests/test_readers_*`、`tests/test_detect_*`、`tests/test_search_*`、`tests/test_convert_*`、`tests/test_compare_*`、`tests/test_edit_*`，不共享测试文件。

### 2.4 不建议切片的部分（必须串行）

| 部分 | 原因 |
|---|---|
| 契约（数据类 + API） | 并行开发的地基，切了就会各写各的 |
| 服务骨架与静态托管 | 所有切片的前置；同时也是 Lead 的集成入口 |
| 采集层（A）与结构识别（B）的联调 | 判据必须在真实文件上反复调，两人来回传接口比一人做慢 |
| 端到端集成与真机验收（WPS 打开输出文件） | 需要全局视角，且是本项目唯一的人工验收环节 |
| 启动脚本/README/打包 | 收口期一次成型，避免多方修改 |

## 三、质量门与测试策略

| 层级 | 内容 | 责任 |
|---|---|---|
| 单测 | reader（3 格式 × 真实文件快照）、detect（台账/工单/无表头表）、normalize（全半角/日期/手机号）、index（召回/打分）、mapping（列→列/转置/区域）、compare（增删改/重复键/左右坐标）、edit（三种值类型写回 + 自检 + 回滚） | 各切片自测，Lead 抽查 |
| 契约测试 | 所有 API handler 用 mock 输入跑通，响应结构与冻结契约一致；**搜索/对比响应必须含完整 `CellRef` 字段** | S0 建立，切片遵守 |
| 端到端 | 真实目录：扫描→索引→搜索→编辑→映射（含转置）→生成→对比→导出 | Lead 收口 |
| 人工验收 | ①随机单元格可检索且带文件/行/列 ②生成台账 WPS 打开无修复提示 ③差异结果与人工一致且带左右坐标 ④改一个格子后文件仍可正常打开 | Lead + 用户 |

**每个切片完成的定义（DoD）**：代码 + 单测通过 + 该域 API 在真实数据上跑通 + 更新本切片在 README/接口表中的说明。

## 五、切片决策记录（TL;DR）

- **要切**：体量 7k+ 行、7 个单向依赖的能力域、写作用域天然不重叠；
- **切 6 个开发切片**：S1 采集、S2 识别、S3 检索、S4 映射与模板（含转置）、S5 对比、S8 编辑写回，加 S6 前端，共 **7 个开发切片**，外加 Lead 的 S0 契约与 S7 收口；
- **先冻契约再并行**：`model.py`（含 `CellRef`/`TemplateDef`/`MappingRule`/`EditOp`）+ JSON API 是唯一同步点，冻结前不开工；
- **不切的**：契约、骨架、A+B 联调、端到端验收、打包 —— 全部由 Lead 串行兜住；
- **最大剩余风险**在 S4（样式保真 + 转置语义）、S8（写坏文件不可逆）与 S2（表头判据）：S4/S8 在 P1 各先跑"模板包结构探路"和"单格写回探路"，S2 在 P1 用 fixture 先行，把风险前移。
